## SGE Execution Environment (Docker)

The analysis execution feature submits shell scripts to a Sun Grid Engine (SGE) queue inside a Docker container. The backend expects a container named `sge-master` and a `shared/` directory mounted at `/shared` in the container.

```bash
cd docker
docker compose -f docker-compose.sge.yml up -d

# Verify the queue is healthy
docker logs sge-master
docker exec sge-master bash -c 'source /opt/sge/default/common/settings.sh && qstat -f'
```

Scripts are written to `SHARED_DIR` (default `shared/`) and submitted with:

```bash
docker exec sge-master bash -c 'source /opt/sge/default/common/settings.sh && qsub -o /shared /shared/<script>.sh'
```

See `docker/SGE-Docker-Setup.md` for troubleshooting queue errors.

## Neo4j Graph Database (Docker)

A demo Neo4j instance is available under `neo4j-docker-compose/`. It starts a non-persistent `neo4j:5` container and an `init` sidecar that imports `data.json` on every fresh startup.

```bash
cd neo4j-docker-compose

# Start (or re-initialize from data.json)
docker compose down
docker compose up -d

# Watch initialization logs
docker logs -f bioflow-neo4j-init
```

Access:
- Neo4j Browser: http://localhost:7474
- Bolt: `bolt://localhost:7687`

Credentials are read from `.env`:

```
NEO4J_USERNAME=neo4j
NEO4J_PASSWORD=bioflow123
NEO4J_AUTH=neo4j/bioflow123
```

The `init.py` sidecar wipes existing data (`MATCH (n) DETACH DELETE n`) and then creates nodes/relationships defined in `data.json`. Because no volumes are mounted, the graph is recreated from `data.json` each time the containers are recreated.

### Data Model

The current `data.json` is generated by `generate_data_json.py` from `scripts/Amplicon/reference/*.md`:

- `Tool` nodes — one per reference `.md`, with properties from the `基本信息` table: `name`, `description`, `scope`, `estimated_time`, `quotation_score`, plus `category` and `script_path` from the backend registries.
- `IO` nodes — one per distinct input/output **description**. Because IO nodes are shared by description, the same node can be the output of one tool and the input of another. Properties include `description`, `filenames`, `formats`, `omics`, `species`, and `examples` (aggregated as arrays when the same description has multiple concrete files).

Relationships:
- `IO -[:input]-> Tool` — this file is consumed by the tool
- `Tool -[:output]-> IO` — this file is produced by the tool

Example query showing a shared file:
```cypher
MATCH (producer:Tool)-[:output]->(io:IO)<-[:input]-(consumer:Tool)
WHERE io.description = 'ASV 代表序列（QIIME2）'
RETURN producer.id, io.description, consumer.id
```

### Plan Service

`app/services/neo4j_plan_service.py` loads the full Neo4j graph into memory and uses BFS to find executable tool paths from given input IOs to target output IOs. A path is "executable" only if every Tool in it has all its input IOs satisfied by the initial inputs or by earlier Tools' outputs.

```python
from app.services.neo4j_plan_service import Neo4jPlanService

paths = Neo4jPlanService.find_paths(
    input_descriptions=["均一化 ASV 表", "样本分组文件"],
    output_descriptions=["DCA 排序图（SVG 格式）"],
    max_paths=3,
)
# paths = [["amp-dca"], ["amp-krona", "amp-dca"], ["amp-alpha-data", "amp-dca"]]
```

Environment variables (with defaults):
- `NEO4J_URI` — default `bolt://localhost:7687`
- `NEO4J_USERNAME` — default `neo4j`
- `NEO4J_PASSWORD` — default `bioflow123`

## Architecture

FastAPI bioinformatics backend with **Laravel-style layered architecture**:

```
HTTP Request → Route (routes/) → Controller (app/http/controllers/) → Service (app/services/) → Model (app/models/) → Database
                                    ↓
                              Pydantic Request (app/http/requests/) for validation
```

All routes mount under `/api` via `routes/api.py`. Static file serving at `/uploads` for uploaded files (`main.py`).

### Model Base Class

All models inherit from `Model` (`app/models/model.py`), which provides:
- Automatic timestamps (`created_at`, `updated_at`)
- Soft delete (`deleted_at` is an **Integer** timestamp, default `0`, not `NULL`)
- Laravel-like methods: `find()`, `all()`, `where()`, `with_trashed()`, `only_trashed()`, `save()`, `delete()`, `force_delete()`, `restore()`

**Field conventions:** All columns must specify `nullable` and a `default`. Required fields use `nullable=False` with type-appropriate defaults (`''` for String/Text, `0` for Integer). Foreign keys use `nullable=False, default=0`.

**Column ordering:** Concrete models redeclare `id`, `created_at`, `updated_at`, `deleted_at` to ensure defined column order in SQLite.

**Serialization:** Models override `to_dict()` for custom output (e.g., `User.to_dict()` hides `hashed_password`, includes `roles`/`permissions`; DateTime fields formatted via `.isoformat()`).

### Domain Model Relationships

```
User
├── projects (Project.user_id) ─── tasks (Task.project_id) ─── messages (Message.task_id)
├── tasks (Task.user_id)
├── templates (Template.user_id)
└── roles (M2M via UserRole) ─── permissions (M2M via RolePermission)
```

Script system: `ScriptFolder` (tree, `parent_id`) → `Script` (tools with `tool_id`, `inputs`, `outputs`, `file_path`).

### RBAC

- `user_roles` — User ↔ Role (M2M)
- `role_permissions` — Role ↔ Permission (M2M)
- `User.to_dict()` automatically includes roles and deduplicated permissions
- Seed: `admin` gets all permissions; `user` gets create+read on projects/tasks/messages

### Authentication

JWT via `python-jose` + `passlib`. Protected routes use `current_user: User = Auth`:

```python
from app.http.middleware import Auth

@router.get("/protected")
def protected_route(current_user: User = Auth):
    return current_user.to_dict()
```

Login returns `{"token": "...", "user": {...}}` (field name is `token`, not `access_token`). Token expiry is 7 days.

## Chat & Analysis Pipeline

The core feature is an LLM-driven bioinformatics analysis assistant. The interaction flow is:

1. **User sends message** → `ChatService.chat()` creates/updates Task + Message
2. **Parse intent** → `ParserService.parse()` (LLM first via `llm_parser.py`, keyword fallback via `nl_parser.py`) extracts `available_inputs` + `goal_types`
3. **Route decision** → Based on what's known (inputs, goals, both, neither):
   - Neither → clarification prompt
   - Only inputs → ask for goals
   - Only goals → ask for data type
   - Both → run planner
4. **Plan workflow** → `PlannerService` calls BFS planner (`pkg/amplicon/planner.py`) to find tool chains
5. **User confirms path** → `ChatService.confirm_path()` saves the selected path and returns `required_files` (does **not** generate code yet)
6. **User uploads files** → `ChatService.confirm_upload()` validates extensions and archive integrity, then generates the orchestration script via `pkg/amplicon/orchestrator.py`
7. **Execute** → `ChatService.start_execution()` writes the script to `SHARED_DIR`, creates an `Execution` record, and runs `docker exec sge-master qsub`
8. **Monitor** → `ChatService.get_execution_logs()` reads the SGE log (`task_{id}.o{qsub_id}`) from `SHARED_DIR` and updates the `Execution` record
9. **Retry / re-upload** → `ChatService.retry_execution()` resubmits the last execution's script as a new `Execution`; `ChatService.reupload_and_execute()` re-validates uploads and then starts a new execution

Message types: `"text"`, `"clarification"`, `"workflow"`, `"file_request"`, `"select_path"`, `"code"`.

### Execution Records

The `Execution` model (`app/models/execution.py`) persists every analysis run:

```
status: pending → running → completed / failed / cancelled
tool_ids, script_content, script_path, qsub_id, log_content, error_message
```

`ExecutionService` (`app/services/execution_service.py`) handles lifecycle transitions and keeps the parent `Task.status` in sync.

### Amplicon Tool System (`pkg/amplicon/`)

The analysis pipeline is built around a tool registry where each tool maps **input data types → output data types**:

- **`amplicon_tools.py`** — `ToolDef` registry (`get_all_tools()`), data type name mappings (`DATA_TYPE_NAMES`), file requirement definitions (`DATA_TYPE_TO_FILE_REQUIREMENT`), and `resolve_root_inputs()` to derive user-required uploads from a tool chain
- **`planner.py`** — Two-phase BFS planner: Phase 1 finds core paths to intermediate states, Phase 2 attaches terminal tools. Returns up to `top_n` `WorkflowCandidate`s
- **`orchestrator.py`** — Generates the final bash orchestration script after file uploads, wiring uploaded files and tool parameters together
- **`nl_parser.py`** — Keyword-based fallback parser (Chinese + English keywords)
- **`llm_parser.py`** — LLM-based parser using DashScope, includes `SYSTEM_PROMPT` (structured JSON parsing) and `CLARIFICATION_SYSTEM_PROMPT` (friendly follow-up questions)
- **`code_templates.py`** — Shell script templates per tool ID and `generate_workflow_script()` for fallback code generation

Tool IDs follow `amp-{short-name}` pattern (e.g., `amp-dada2`, `amp-lefse`, `amp-pca`). Categories: 数据预处理, 质量控制, 核心分析, 多样性分析, 统计检验, 可视化, 排序分析, 功能预测.

Seed data (`migrate_seed.py`) auto-populates `Script` records from `get_all_tools()`, mapping each tool to its shell script in `scripts/Amplicon/`.

### Script Code Generation

When a user uploads files, `ChatService.confirm_upload()` calls `generate_orchestrator_script()` to produce a single concatenated bash script with correct parameter passing. The orchestrator resolves uploaded file paths under `/shared/`, handles `FASTQ_PAIR` R1/R2 sample grouping, and emits container-aware environment overrides (`PATH`, `RSCRIPT_BIN`, `PERL_BIN`, `CONVERT_BIN`).

`ChatService._generate_script_with_llm()` is a legacy LLM-based generator that is no longer on the main path but remains in the codebase.

## Database

SQLAlchemy ORM with SQLite. Sessions via `Depends(get_db)` or `SessionLocal()`. Tables auto-created by `migrate_seed.py`, which also runs incremental migrations (e.g., `migrate_messages_v2` adds structured columns, `migrate_tasks_v2` adds `qsub_id`/`script_path`, `migrate_executions_v1` adds the executions table).

## Adding New Features

1. **Model** (`app/models/`) — inherit `Model`, redeclare `id`/`created_at`/`updated_at`/`deleted_at`
2. **Service** (`app/services/`) — static methods on a class
3. **Controller** (`app/http/controllers/`) — delegates to service
4. **Request** (`app/http/requests/`) — Pydantic `BaseModel`
5. **Route** (`routes/`) — `APIRouter`, register in `routes/api.py`
6. **Migrate** — `python migrate_seed.py`
