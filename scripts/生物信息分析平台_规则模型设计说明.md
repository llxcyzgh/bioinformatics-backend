# 生物信息自然语言分析平台：规则模型设计说明（面向开发实现）

## 1. 文档目的

本文档用于明确平台首版中“路径规划求解”的核心实现方式。目标不是构建一个复杂的图数据库或通用规划器，而是采用**轻量规则模型 + 状态搜索**的方式，在工程复杂度可控的前提下，实现从自然语言分析目标到候选工作流的自动生成。

本文档面向开发人员，重点说明：

- 为什么采用规则模型
- 规则模型中的核心对象是什么
- 数据结构如何设计
- 路径求解如何实现
- 首版应做到什么程度
- 哪些能力暂不纳入首版

---

## 2. 总体设计原则

### 2.1 不把“图”作为首版实现核心

从理论上讲，这个问题可以理解为图问题，甚至更准确地说是超图问题，因为一个工具通常具有：

- 多个输入
- 多个输出
- 只有全部输入满足时才可执行

但首版实现不建议直接围绕“图数据库”或“超图引擎”展开，而应采用更容易实现、也更容易调试的方案：**规则模型**。

### 2.2 用规则表达工具能力

每个工具不再被当作一段随意调用的 shell 脚本，而是被抽象成一条规则：

`输入类型集合 -> 输出类型集合`

例如：

- `FASTQ_PAIR + REFERENCE_GENOME -> BAM`
- `BAM -> SORTED_BAM`
- `SORTED_BAM + REFERENCE_GENOME -> VCF`

求解时，不是从某个“节点”走到另一个“节点”，而是从当前已有的数据类型集合出发，寻找哪些规则可以被触发，并逐步扩展到目标结果。

### 2.3 首版追求“足够正确、足够稳定、足够易实现”

首版设计不追求理论最优，也不追求支持所有复杂场景。重点是：

- 数据结构清晰
- AI 能辅助实现
- 逻辑容易验证
- 结果可解释
- 后续可扩展

---

## 3. 核心对象

首版规则模型建议围绕以下五类核心对象实现：

1. `Tool`：标准工具
2. `DataType`：数据类型
3. `PlanningRequest`：规划请求
4. `PlanningState`：规划状态
5. `WorkflowCandidate`：候选工作流

---

## 4. DataType 设计

### 4.1 设计目标

`DataType` 用于描述工具输入输出之间的衔接关系。首版不建议引入过于复杂的生物信息本体体系，而应先定义一组**标准化、可枚举的数据类型**。

### 4.2 首版建议的数据类型表示

首版建议把数据类型定义为：

- 一个主类型标识
- 少量关键属性
- 可选的人类可读说明

### 示例

```json
{
  "type_id": "FASTQ_PAIR",
  "display_name": "双端测序原始文件",
  "category": "sequence_input",
  "attrs": {
    "paired": true
  }
}
```

```json
{
  "type_id": "SORTED_BAM",
  "display_name": "已排序比对结果",
  "category": "alignment_result",
  "attrs": {
    "format": "BAM",
    "sorted": true
  }
}
```

### 4.3 首版建议的数据类型范围

首版不要追求完备，只覆盖首期场景中真正会出现的核心类型。例如：

- `FASTQ_SINGLE`
- `FASTQ_PAIR`
- `REFERENCE_GENOME`
- `BAM`
- `SORTED_BAM`
- `VCF`
- `ANNOTATED_VCF`
- `EXPRESSION_MATRIX`
- `QC_REPORT`

如果属性体系实现起来过重，也可以在首版中直接把一些关键状态拆成不同类型，例如：

- `BAM`
- `SORTED_BAM`

而不必一开始就通过复杂属性判断二者差异。

## 5. Tool 设计

### 5.1 设计目标

每个 shell 脚本在进入求解器前，必须先被标准化为 `Tool`。求解器不直接依赖原始脚本，而依赖标准工具描述。

### 5.2 Tool 的最小字段

首版建议每个工具至少包含以下字段：

- `tool_id`：工具唯一标识
- `tool_name`：工具名称
- `description`：用途说明
- `inputs`：输入类型列表
- `outputs`：输出类型列表
- `params`：参数定义
- `script_ref`：关联原始脚本
- `enabled`：是否启用
- `priority`：排序权重
- `scenario_tags`：适用场景标签

### 示例

```json
{
  "tool_id": "align_bwa",
  "tool_name": "BWA 比对",
  "description": "将双端 FASTQ 与参考基因组比对，生成 BAM",
  "inputs": ["FASTQ_PAIR", "REFERENCE_GENOME"],
  "outputs": ["BAM"],
  "params": [
    {
      "name": "threads",
      "type": "integer",
      "required": false,
      "default": 8
    }
  ],
  "script_ref": {
    "path": "dna/alignment/bwa_align.sh",
    "version": "1.0.0"
  },
  "enabled": true,
  "priority": 10,
  "scenario_tags": ["variant_calling", "dna_seq"]
}
```

### 5.3 后续可扩展字段

首版不强依赖，但建议预留：

- `validation_status`
- `preferred_status`
- `deprecated`
- `owner`
- `resource_profile`
- `warnings`

---

## 6. PlanningRequest 设计

### 6.1 设计目标

`PlanningRequest` 表示一次路径规划请求，是自然语言需求解析之后的结构化输入。

### 6.2 核心字段

- `goal_types`：目标输出类型列表
- `available_inputs`：当前已有输入类型列表
- `required_inputs`：理论必需输入类型列表
- `constraints`：约束条件
- `scenario_tags`：场景标签
- `max_depth`：最大搜索深度
- `top_n`：返回候选方案数量

### 示例

```json
{
  "goal_types": ["VCF"],
  "available_inputs": ["FASTQ_PAIR", "REFERENCE_GENOME"],
  "required_inputs": ["FASTQ_PAIR", "REFERENCE_GENOME"],
  "constraints": {},
  "scenario_tags": ["variant_calling"],
  "max_depth": 6,
  "top_n": 3
}
```

---

## 7. PlanningState 设计

### 7.1 设计目标

规划过程中的“状态”不是当前位置，而是**当前已经拥有的数据类型集合**。

这也是首版求解器最重要的思想。

### 7.2 核心字段

- `available_types`：当前已有的数据类型集合
- `used_tools`：当前路径中已使用的工具序列
- `produced_types`：本轮求解新增的数据类型
- `depth`：当前深度

### 示例

```json
{
  "available_types": ["FASTQ_PAIR", "REFERENCE_GENOME", "BAM"],
  "used_tools": ["align_bwa"],
  "produced_types": ["BAM"],
  "depth": 1
}
```

---

## 8. WorkflowCandidate 设计

### 8.1 设计目标

`WorkflowCandidate` 表示求解器产出的一条候选方案。

首版中候选方案可以先按“步骤序列”表示；后续如果需要支持并行分支，再扩展成 DAG 结构。

### 8.2 核心字段

- `candidate_id`
- `tool_chain`
- `final_types`
- `missing_inputs`
- `score`
- `explanation`

### 示例

```json
{
  "candidate_id": "wf_001",
  "tool_chain": ["align_bwa", "sort_bam", "variant_call"],
  "final_types": ["VCF"],
  "missing_inputs": [],
  "score": 0.92,
  "explanation": "该方案基于双端 FASTQ 和参考基因组生成 VCF，步骤较短，所用工具均为已启用工具。"
}
```

## 9. 求解器核心逻辑

### 9.1 求解问题定义

给定：

- 一组已拥有的数据类型
- 一组目标数据类型
- 一组标准工具规则

求解器需要输出若干条可行方案，使得通过顺序执行这些工具后，可以从已有输入扩展到目标输出。

### 9.2 基本求解流程

首版建议采用**受限 BFS / Best-First Search**。

基本流程如下：

1. 初始化状态：`available_types = 用户已有输入`
2. 遍历所有工具，找出输入条件已满足的工具
3. 对每个可执行工具，生成新状态
4. 若新状态中包含目标输出，则记录为候选方案
5. 继续扩展，直到：
   - 达到 `top_n`
   - 达到 `max_depth`
   - 无可扩展状态

### 9.3 伪代码

```python
def plan(tools, initial_types, goal_types, max_depth=6, top_n=3):
    queue = []
    results = []
    visited = set()

    init_state = State(
        available_types=frozenset(initial_types),
        used_tools=[],
        depth=0
    )
    queue.append(init_state)

    while queue and len(results) < top_n:
        state = queue.pop(0)

        if any(goal in state.available_types for goal in goal_types):
            results.append(state)
            continue

        if state.depth >= max_depth:
            continue

        for tool in tools:
            if not tool.enabled:
                continue

            if all(req in state.available_types for req in tool.inputs):
                new_types = set(state.available_types) | set(tool.outputs)

                if frozenset(new_types) == state.available_types:
                    continue

                new_state = State(
                    available_types=frozenset(new_types),
                    used_tools=state.used_tools + [tool.tool_id],
                    depth=state.depth + 1
                )

                state_key = (new_state.available_types, tuple(new_state.used_tools))
                if state_key in visited:
                    continue

                visited.add(state_key)
                queue.append(new_state)

    return results
```

## 10. 可执行工具判断

工具是否可执行，应满足以下条件：

1. 工具已启用
2. 其 `inputs` 中所有必需类型均已在当前状态出现
3. 执行后能够产生至少一种新的输出类型

首版不建议在求解阶段引入过多复杂条件，例如动态环境判断、复杂资源判断等。这些可以在执行阶段再做更细校验。

---

## 11. 候选路径排序

首版建议采用简单排序，不追求复杂评分模型。

可参考以下因素：

- 路径长度较短优先
- 工具优先级较高优先
- 已验证/推荐工具优先
- 缺失输入较少优先

首版排序策略应尽量简单透明，便于调试和解释。

---

## 12. 输入缺失判断

在输出候选方案时，平台需要告诉用户还缺少哪些输入。

方法很简单：

1. 取该候选方案中所有工具的输入集合
2. 减去：
   - 用户已提供的输入
   - 平台可自动提供的公共资源
   - 方案内前序步骤会产出的类型
3. 剩余部分即为缺失输入

### 示例

如果用户已提供：

- `FASTQ_PAIR`

平台自动提供：

- `REFERENCE_GENOME`

某方案需要：

- `FASTQ_PAIR`
- `REFERENCE_GENOME`

则缺失输入为空。

如果某方案还需要 `ANNOTATION_DB`，而该对象既不是用户输入，也不是平台预置资源，则应提示用户补充。

---

## 13. 从候选方案到可执行流程

求解器输出的只是工具链，不是最终执行脚本。

执行前还需要做一层编译：

1. 为每个工具绑定实际输入来源
2. 为每个输出分配物理路径
3. 生成步骤顺序
4. 渲染参数
5. 生成结构化流程定义
6. 再由流程定义编译为 shell pipeline

因此建议定义独立的 `WorkflowSpec` 作为执行前的中间对象。

### 示例

```json
{
  "workflow_id": "wf_001",
  "steps": [
    {
      "tool_id": "align_bwa",
      "bindings": {
        "FASTQ_PAIR": "input/sample.fastq.gz",
        "REFERENCE_GENOME": "ref/hg38.fa"
      },
      "outputs": {
        "BAM": "work/step1/output.bam"
      },
      "params": {
        "threads": 8
      }
    }
  ]
}
```

## 14. 首版范围建议

首版建议只支持以下能力：

- 少量标准数据类型
- 少量高频分析场景
- 线性工具链求解
- Top 3 候选方案
- 简单排序
- 输入缺失提示
- 结构化流程定义生成
- shell pipeline 编译

首版暂不建议支持：

- 复杂并行 DAG 求解
- 复杂资源优化
- 非确定性规则
- 工具运行成本精细建模
- 全自动参数寻优
- 过于开放的自然语言理解

---

## 15. 为什么首版推荐规则模型而不是复杂图方案

从理论上讲，超图更准确，但对首版实现来说，规则模型更合适，原因如下：

1. 工程实现简单，适合快速落地
2. 更容易由 AI 辅助设计和编码
3. 调试和验证成本更低
4. 已经能够准确表达“多输入 -> 多输出”的工具关系
5. 后续若需要，也可以平滑演进到更复杂的图或 DAG 表达

因此，首版实现建议采用：

- `Tool` 作为规则载体
- `DataType` 作为衔接对象
- `PlanningState` 作为求解状态
- `WorkflowCandidate` 作为求解结果

---

## 16. 推荐的首版开发顺序

建议开发顺序如下：

1. 定义 `DataType` 和 `Tool` 的 JSON Schema
2. 完成工具注册表的存储与读取
3. 完成 `PlanningRequest` 结构
4. 实现基础 BFS 求解器
5. 实现候选方案排序
6. 实现输入缺失判断
7. 实现 `WorkflowSpec` 结构
8. 实现 `WorkflowSpec -> Shell Pipeline` 编译
9. 再接入前端和自然语言需求解析模块

这样分阶段实现，有利于逐步验证每一层的正确性。

---

## 17. 一句话总结

首版路径规划不建议直接实现复杂图系统，而建议采用“工具规则 + 数据类型 + 状态搜索”的轻量方案。该方案能够在工程复杂度可控的前提下，较准确地完成候选分析路径生成，并且易于后续扩展和维护。
